# kamal-panel

[English](README.md) | **简体中文**

一个（基本上）只读的 [Kamal](https://kamal-deploy.org/) 部署控制面板：用一张「应用 × 主机」
总览表，几秒钟回答「有没有哪里出问题了」，不用再挨个 SSH 上机器手敲 `kamal app details`。

kamal-panel **不是** Kamal 的替代品。它通过 SSH 读取 Kamal 本来就会产生的状态
（`docker ps`、`kamal-proxy list --json`）并把它渲染出来。部署仍然照旧由 CI 执行
`kamal deploy`。

---

## ⚠️ 安全边界 —— 部署到任何地方之前先读这一节

> **面板的安全级别，等于它所管理的每一台服务器的安全级别。**
> 任何能访问到面板并读到它数据库的人，都可以间接地操作你的基础设施。
> 请把它当作一把 SSH 私钥来对待。

- **每个页面都要求已登录用户。** 共有三种角色 —— **admin**、**developer** 和 **ops**，
  见下面的「角色」一节。`POST /apps`（「添加应用」接口）、凭据管理和人员管理都需要
  **admin**；动作接口要求 admin，或者是该应用的 developer 成员。第一个账号怎么创建，
  见下面的「部署：第一个 admin 账号」。SSO 不在本项目范围内。
- **添加一个应用等于执行代码，而不是填配置。** 解析粘贴进来的 `deploy.yml` 需要先求值
  ERB，再对结果做 `YAML.unsafe_load` —— Kamal 自己就是这么做的，想保留 ERB 支持就绕不开。
  本面板把这段解析放在一个隔离的、限制了资源和时间的子进程里执行（见设计文档 §7.6），
  但现实后果不变：**任何能向这个面板提交 `deploy.yml` 的人，都能在面板所在的主机上运行
  任意 Ruby 代码。** 不要让不受信任的用户接触到「添加应用」表单。
- SSH 私钥在库中是加密存储的（Rails 8 的 Active Record encryption），并且是**只写**的：
  界面永远不会展示或下载已存储的私钥，只显示它的指纹。

## 角色

所有已登录用户都能看到所有应用，区别在于能*做*什么。

- **admin** —— 全部权限：添加和停用应用、管理 SSH 与镜像仓库凭据、管理人员、给应用分配
  凭据，以及对任意应用执行任意动作。
- **developer** —— 可以回滚、重启、停止、启动、强制解除卡住的部署锁，但**仅限于自己是成员
  的那些应用**。成员关系由 admin 按应用逐个指派。在自己不属于的应用上，developer 看到的
  和 `ops` 一样是只读视图。
- **ops** —— 全局只读，只有一个例外：`ops` 可以对任意应用执行非变更类的**日志**动作。
  回滚、重启、停止、启动、强制解锁，在任何地方都不行。

面板对你没有权限的东西选择**隐藏**而不是置灰 —— 按钮和导航项都是如此 —— 这样没人需要去猜
自己到底能做什么。已停用的应用不接受任何人的动作，admin 也不行。

> **添加应用等价于在面板自己的主机上执行代码。** 粘贴进来的 `deploy.yml` 会被 ERB 求值
> （见上面的安全一节），这也正是该接口仅限 admin 的原因。

破坏性操作光有角色还不够：提交前会先列出受影响的主机和角色，而回滚与强制解锁还额外要求
你手动输入应用名称。每一次动作都会在**执行之前**先写入审计日志（状态 `pending`），
并且这份日志既无法从界面删除，也无法通过 Active Record 删除。

## 面板是怎么执行写操作的

面板**从不自己拼装远程命令**。回滚、重启、停止、启动、强制解锁，全部是在一个受限子进程里
调用真正的 `kamal` CLI，因此行为与你自己敲 `kamal rollback` 完全一致 —— 包括你自己的
pre/post-deploy 钩子、`kamal-proxy` 的路由切换，以及健康检查。如果基于
`Kamal::Commands::App` 重新实现一遍，就等于要长期维护第二套必须永远和 Kamal 保持一致的实现。

有两个后果值得知道：

- 私钥是通过**每次调用新建的 `ssh-agent`** 注入的（`ssh-add -` 从标准输入读取）；它从不落盘，
  连 0600 权限的临时文件都不写。
- 动作集合是**封闭的、写死在代码里的**（`app/services/actions/`）。没有自由文本命令输入框，
  加一个就会让这里所有其他安全决策失效。

因为面板不把命令的退出码当作最终结论，动作结束后会触发一小段密集轮询：「到底成没成功」
这个答案来自新鲜的 `docker ps` 观测结果，而不是 CLI 的返回码。

回滚只会列出它能证明可回滚的版本：`kamal rollback` 要求那个版本的容器在**每一台**主机上
都还在，否则会拒绝执行；而面板本来就持有每台主机完整的 `docker ps --all` —— 所以不可用的
版本会以置灰形式列出，并指明容器已经在哪台主机上被清理掉了，而不是等你点下去之后才报错。

## 部署上报（可选）

SSH 轮询能回答「现在跑着什么」，但回答不了「这是谁部署的、什么时候、上一次是不是失败了」——
一次失败的部署不会改变正在运行的版本，所以轮询根本看不到任何变化。

Kamal 在部署过程中本来就会执行你的 `.kamal/hooks/*`，并传给它们 `KAMAL_SERVICE`、
`KAMAL_VERSION`、`KAMAL_PERFORMER`、`KAMAL_DESTINATION`、`KAMAL_RECORDED_AT`
和 `KAMAL_COMMAND`。面板会在每个应用的详情页为你生成两段 `curl` 片段 —— 一段给
`pre-deploy`，一段给 `post-deploy` —— 并把它们上报的内容存为部署历史。

**这一步是可选的。** 不做也不影响其他功能，只是拿不到部署历史，面板也无法告诉你
「这个版本被上报为已部署，但从来没在任何机器上出现过」。

生成的片段里有两点不可妥协，你做任何修改后都应该检查它们还在：

- `--max-time 5` 和结尾的 `|| true`。**面板挂掉或者变慢，绝不能让你的部署失败或卡住。**
- 钩子文件需要可执行位（`chmod +x`）—— Kamal 是把它们当可执行文件来跑的。

上报 token 按应用维度生成，并且**只显示一次**，就在生成的那一刻；面板只存它的 SHA256
摘要，无法再次展示给你。重新生成会立即使上一个失效。

当上报说某个版本部署成功、但 90 秒内没有观测到任何机器在运行它时，面板会在应用页面上直接
说明这一点，而不是在两个信息源之间挑一个来相信。一旦观测到该版本，警告会自动消失，但历史
记录里会保留这段延迟 —— 这样「每次部署都要四分钟才真正生效」这种规律才能被看见。

即使不配置钩子，你也能拿到*一部分*历史：每次轮询都会比对各台主机上运行的版本，当它们全部
收敛到一个与上次不同的版本时，面板会把这记录为一次推断出的部署。这能给你「有东西被部署了，
以及时间」—— 但没有执行人、没有命令、也没有失败的部署，因为失败的部署不会改变正在运行的
版本。这三样只能来自钩子。

## 刻意*不做*的事

| 不做 | 为什么 |
|---|---|
| 构建或发布新版本 | 面板永远不碰你的源代码。新的构建来自 CI 执行 `kamal deploy`。 |
| Git 集成 | `deploy.yml` 靠手工粘贴。面板从不持有任何 git 凭据。 |
| `kamal app exec` / 任意远程 shell | 这是唯一一个会把面板变成「网页版远程 shell」、并让本项目其他所有安全决策统统作废的功能。这是刻意的省略，不是待办事项。 |
| 支持 Kamal 1.x | 只支持 **Kamal 2+**。Kamal 1.x 用的是 Traefik 而不是 `kamal-proxy`，容器标签模型、部署锁格式和路由方案都不同 —— 两边都支持就意味着要维护两套并行的采集与执行路径。 |
| SSO | 账号存在面板自己的数据库里。共三种角色（admin、developer、ops），外加 developer 的按应用成员关系 —— 不接外部身份提供方。 |
| 超过约 50 台主机的机群 | 见下一节。 |

## 规模上限

本设计的目标是**最多约 50 台主机**。每次轮询都会为每个受管应用的每台已配置主机拉起一条 SSH
连接；超过大约 50 台之后，这种扇出就会成为瓶颈，而那时正确的解法是换一种架构（比如上 agent），
而不是换一台更大的机器。如果你的机群规模接近或超过这个量级，这个工具（暂时）不适合你。

## 快速开始（开发环境）

### 1. Ruby 与依赖

Ruby 版本见 `.ruby-version`。然后：

```sh
bin/setup
```

### 2. Active Record 加密凭据（必须）

SSH 私钥通过 Rails 8 的 `active_record_encryption` 存储，而它的密钥**只从环境变量 /
Rails credentials 读取**，绝不硬编码。跳过这一步你就无法保存 SSH 私钥，也就意味着
根本无法在界面上把一个应用接入完成：

```sh
bin/rails db:encryption:init
```

按命令输出的提示，把生成的密钥写入开发环境的 credentials
（`bin/rails credentials:edit --environment development`），或写入对应的
`AR_ENCRYPTION_*` 环境变量（见 `config/application.rb`）。

### 3. 数据库

```sh
bin/rails db:prepare
```

### 4. 演示数据（可选，但第一次看强烈建议）

刚装好的面板是一张空白页，而这个东西的全部意义恰恰在于*出问题时*它长什么样。一条命令就能把
开发数据库填满五个覆盖各种状态的应用 —— 健康、版本漂移、容器不健康、主机不可达、以及从未
轮询过 —— 外加两种对账告警、来自两个来源的部署历史，还有成功、失败和仍在运行中的审计记录：

```sh
bin/rails demo:seed
```

它拒绝在非 development 环境运行，也拒绝运行第二次（审计日志按设计不可删除，所以不存在
「清空后重新灌」这种操作 —— 需要的话用 `bin/rails db:reset`）。

## 运行测试

测试套件会对两个容器化的「假主机」发起真实 SSH，它们模拟的是跑着 Kamal 部署容器和
`kamal-proxy` 的机器。因此本地需要有 Docker 在运行。

```sh
docker compose -f docker-compose.test.yml up -d --build
```

等两个节点都起来（compose 文件把 node-1 暴露在 `localhost:2201`、node-2 在 `localhost:2202`）；
关于这套 fixture 本身的细节见 `test/fake_host/README.md`，其中也解释了为什么新克隆仓库后需要
对签入的测试 SSH 私钥执行 `chmod 600`，系统的 `ssh` 客户端才肯接受它。

然后跑整个套件：

```sh
bin/rails test:all
```

**请在前台、以单进程方式运行。** 这个套件有两条不可商量的约束：

- **绝不要在 `RAILS_ENV=test` 下用 `bin/rails runner` 对测试数据库触发轮询。**
  `bin/rails runner` 会启动一个*独立的*进程；它写的任何东西都会落进测试套件正在使用的同一个
  SQLite 测试库，并破坏当时正在跑的任意一个测试。如果你要拿测试 fixture 做实验，请在
  `bin/rails console -e test` 里串行地做，绝不要和 `bin/rails test` 并行。
- **不要并行跑测试。** 套件有几个地方依赖 SQLite 的单写者语义（具体那一处见设计文档 `10.1`：
  轮询去重），也依赖对假主机容器的独占访问（有些测试确实会停止/启动容器来模拟主机不可达）。
  并行开 worker，或者同时让另一个 `bin/rails` 进程访问测试库，都会产生偶发、难以复现、
  且与你改的代码毫无关系的失败。

单跑 `bin/rails test` **不**包含系统测试（Rails 默认排除 `test/system`）；想要完整覆盖请用
`bin/rails test:all`（或者在 `bin/rails test` 之外再跑 `bin/rails test:system`），CI 跑的也是这个。

## 部署：第一个 admin 账号

永远不存在默认密码 —— 一个自带公开凭据的面板比完全没有鉴权更糟，因为它看起来是受保护的。
第一个 `admin` 账号改为在灌种子数据时由环境变量创建：

```sh
KAMAL_PANEL_ADMIN_EMAIL=you@example.com \
KAMAL_PANEL_ADMIN_PASSWORD=<一个强而唯一的密码> \
bin/rails db:seed
```

`db/seeds.rb` 是幂等的（按邮箱做 `find_or_create_by!`），所以重新部署时再跑一次 `db:seed`
是安全的，不会重置已存在账号的密码。如果 `KAMAL_PANEL_ADMIN_EMAIL` 没有设置，灌种子什么也
不做 —— 任何账号，无论是不是 `admin`，都不会被隐式创建。

第一个 admin 存在之后，后续人员在面板内的**人员**页管理（`/users`，仅 admin 可见）：新建
账号、设置角色、指派按应用的成员关系、停用。这里刻意**没有删除** —— 审计记录引用
`users.id` 而审计日志不可删除，所以离职的人是被*停用*，停用会同时立即销毁其已登录会话。
同样刻意没有自助注册流程。

## 部署面板自身

面板用 Kamal 部署，和别的应用没两样。仓库里的 `config/deploy.yml` 是一份带占位符的可用配置 ——
`image`、`servers.web` 和 `proxy.host` 是你必须改的三行。

```sh
# 一次性：生成 Active Record 加密密钥，并妥善保存
bin/rails db:encryption:init

# 每次部署都从你的 shell 读取这些（见 .kamal/secrets）
export KAMAL_REGISTRY_USERNAME=your-github-user
export KAMAL_REGISTRY_PASSWORD=<一个带 write:packages 权限的 PAT>
export AR_ENCRYPTION_PRIMARY_KEY=... AR_ENCRYPTION_DETERMINISTIC_KEY=... AR_ENCRYPTION_KEY_DERIVATION_SALT=...

bin/kamal setup     # 首次
bin/kamal deploy    # 之后
```

关于这套部署，有两点不是偶然：

- **它按设计就是单机的。** 状态存在 SQLite 里，Solid Queue 跑在 Puma 进程内。加第二台 `web`
  主机不会让面板更稳，只会让你得到两个各持一半真相、而且互不知情的面板。
- **存储卷里放着加密后的 SSH 私钥。** 备份这个卷，等同于备份了通往面板所管理的每一台服务器的
  访问凭据。请以对待那些私钥的谨慎程度对待这份备份 —— 另外注意，丢失那三个 `AR_ENCRYPTION_*`
  值会让这个卷**永久无法解密**，那意味着每一把私钥都得重新录入。

仓库里的 `.kamal/hooks/pre-deploy` 和 `post-deploy` 就是上面「部署上报」一节里那两段片段的
可复用版本：它们从环境变量读取 `PANEL_URL` 和 `PANEL_TOKEN`，在这两个变量未设置时静默退出，
这样一个还没接入面板的仓库就不会在每次部署时对着空气发请求。

### 不要用面板管理面板自己

把面板加进它自己的应用列表是个坑，而面板并不会拦你 —— 所以这里只能用一段警告代替。

*从*面板里重启或停止面板，会在它执行自己命令的中途把进程杀掉。你会得到：一条永远停在
`pending` 的审计记录、一个断在半行的实时输出面板，以及可能仍然被持有在主节点上的 Kamal
部署锁，还得有人手动去强制解锁。那条 `pending` 记录不是数据损坏 —— 它恰恰兑现了审计设计的
承诺（「有人发起过这次操作」），而在这种情况下它是唯一留下的痕迹。

如果你确实想在面板里看到面板自己的部署历史，那就得把它注册为一个应用，届时那些动作按钮对它
也同样存在。这是个取舍；请在知情的前提下做决定。部署面板本身，建议在你自己的工作机上用
`bin/kamal deploy`。
