# kamal-panel 设计 05：从观测推断的部署事件

> 主设计 `2026-09-05-kamal-panel-design.md` 与子设计 `2026-09-07-kamal-panel-hook-reporting-design.md`
> 的续篇。后者第 2 节明确把 `inferred` 事件排除在那一轮之外，本文是对那条排除理由的正面回答。

**Goal:** 让没有配置 hook 上报的应用也有部署历史——但只写面板真的知道的那一件事：
版本变了。

**范围之外：** 深色模式；从观测推断 performer / command / 失败部署（机器上看不出来，
不猜）。

---

## 1. 为什么现在做，以及当初为什么不做

子设计 03 的决策表原文：

> | 本轮是否做 `inferred` 事件 | 否。`source` 字段保留，但只写 `hook` | 不把推测写成事实。
> 从 Observation 推断版本变更要处理滚动部署中途的混合版本、回滚、失联后重现，
> 否则会造出一堆假事件 |

那不是「以后再说」，是三个具体障碍。本文逐个回答：

| 障碍 | 回答 |
|---|---|
| 滚动部署中途的混合版本 | 只在**全体收敛**时记一条（第 2 节）。中途不产生事件，一次部署就是一行 |
| 回滚 | 去重带**时间边界**（第 3 节）。回滚到三个月前的版本照记，不会被那条老事件吞掉 |
| 失联后重现 | 收敛要求**每台 host 都有可达且 running 的观测**（第 2 节）。有机器失联就不算收敛，不记事件 |

代价仍然存在，写在第 6 节：推断给不出 performer、command，也看不见失败的部署。
它补的是「有没有发生过部署」，不是「那次部署是怎么回事」。

## 2. 收敛的定义

取 `Observation.latest_for(managed_app)`（每台机器最新的那一批观测），只看同时满足
以下三条的行：`reachable` 为真、`docker_status` 属于 running / restarting、`version` 非空。

**收敛** = 配置里的每一台 host 都至少有一行这样的观测，**且所有这些行的 version 相同**。

这条定义自动处理了两件事：

- **多角色**：一台机器上 web 已经是 V2 而 worker 还是 V1，两行 version 不同，不算收敛。
- **失联**：任何一台 host 没有可达且 running 的观测，就不算收敛。否则三台机器挂了一台、
  另两台升级完，面板会宣称「已收敛到 V2」，而那台挂掉的可能还跑着 V1。

**不要求观测「新鲜」。** 轮询停摆时那批观测会一直是旧的，但旧的集合不会变化，因此也
不会产生任何事件。多加一个陈旧阈值只是多一个会误判的参数。

收敛时刻取那批 running 观测里**最早**的 `observed_at`——面板是在那一刻才看全的。
`last_converged_at` 存的就是这个时刻，不是 `Time.current`：与 `Reconciler` 回填
`observed_at` 用观测时间而非当下，是同一条理由。

## 3. 状态与去重

`ManagedApp` 新增两列：

- `last_converged_version` —— 上一次收敛到的版本。`nil` 表示**还没建立基线**。
- `last_converged_at` —— 上一次收敛发生的时刻（用于去重的时间边界，见下）。

**基线**：第一次收敛只写这两列，**不产生事件**。一个早就在跑 V1 的应用刚被接进面板，
它不是「今天部署的 V1」——凭空造这条记录，正是子设计 03 拒绝 inferred 时说的「把推测
写成事实」。

**产生事件**：收敛版本与 `last_converged_version` 不同时，记一条 `source: "inferred"`
的 `DeployEvent`，并更新这两列。

**幂等**：收敛版本没变就直接返回。轮询在 burst 期是 2 秒一轮，这条不成立的话历史会被
同一次部署刷屏。

**去重（推断向 hook 让位）**：收敛到版本 V 时，若存在一条 version 为 V、且
`created_at >= last_converged_at` 的既有事件，就不另建推断行——那条 hook 事件本来
就会被 `Reconciler` 回填 `observed_at`，两者说的是同一件事。

两处必须说死，否则实现会分叉：

- 比较用的是**更新之前**的 `last_converged_at`（也就是上一次收敛的时刻），不是本次的。
  边界的含义是「这条上报是不是在当前这一轮收敛期内到达的」。
- **让位时同样要更新那两列。** 否则状态记的是上一版，而每一轮轮询都会重新走一遍
  去重判断——虽然结果都是不记，但状态在撒谎，且下一次真正的版本变更会拿一个错误的
  时间边界去比。

**时间边界不能省。** 若只按 version 去重：回滚到三个月前的 V1 时，库里确实躺着一条
V1 的老 hook 事件，这次回滚就会被静默吞掉——而它明明是一次真实的部署。加上边界之后，
那条老事件早于本轮收敛期，对不上，于是照常记一条推断事件。

## 4. 推断事件长什么样

| 字段 | 值 | 理由 |
|---|---|---|
| `source` | `"inferred"` | `DeployEvent::SOURCES` 从 `%w[hook]` 放宽为 `%w[hook inferred]` |
| `version` | 收敛到的版本 | |
| `started_at` | 空 | 推断不出何时开始 |
| `succeeded_at` | 收敛时刻 | |
| `observed_at` | 收敛时刻（与上一列相同） | 面板确实是在这一刻知道的 |
| `performer` / `command` | 空 | 机器上看不出是谁、用什么命令部的。留空比编一个 "unknown" 诚实 |

**推断事件永远不会触发告警**，这是这套取值的直接结果，也是对的：
`unobserved` 告警要求 `observed_at` 为空，推断事件天生带着它；`unfinished` 告警要求
`started_at` 非空，推断事件天生没有。推断描述的是**已经发生并已被观测到**的事实，
不存在任何矛盾可言。

## 5. 触发点与呈现

**触发点**：新增 `DeployEvents::Inferrer`，与既有的 `Reconciler` 并列挂在
`PollManagedAppJob` 中，各自独立 `begin/rescue`（与两个采集器同样的隔离）。

**顺序有讲究**：先 `Reconciler` 回填 hook 事件的 `observed_at`，再 `Inferrer`。推断要能
看见「这一版刚被回填过」，才谈得上让位。

**部署历史加一列「来源」**，取值是文字：`hook 上报` / `面板推断`。不靠颜色——两类事实
混在一张表里，读的人必须一眼看出哪行是机器说的、哪行是面板推的。

推断行的三处显示要如实：

- `performer` 与 `command` 显示 `—`。
- **「观测」那一列不显示延迟**。延迟的含义是「上报说成功了，面板过了多久才看见」，
  而推断事件根本没有上报，算出来的 0 秒是个没有含义的数字。那一格改为「面板观测到」，
  也就是 `DeployEvent#observation_delay_text` 要为 `inferred` 单独分一支。

**空状态文案要改**。现在写的是「配上部署上报就能在这里看到部署历史」，而从这一轮起，
没配 hook 的应用只要发生一次版本变更也会有历史。改成说清两种来源各自能给到什么。
README 的 Deploy reporting 一节同样补一段。

## 6. 已知限制

- **推断给不出 performer 与 command。** 机器上看不出来。
- **推断看不见失败的部署。** 失败的部署不改变收敛版本，因此不产生任何事件。想看见
  失败，仍然只能靠 hook 的 pre/post 两段（子设计 03 第 5 节的「开了头没收尾」告警）。
- **基线之前的历史无法追溯。** 应用接入面板之前发生过什么，面板不知道，也不假装知道。
- **一台机器长期失联期间不产生任何推断事件。** 那段时间面板确实不知道发生了什么，
  沉默比编造正确。失联本身由既有的 unreachable 观测与总览状态呈现，不归这里管。
- **同一版本被重复部署（CI 重跑同一个 sha）推断不出来。** 收敛版本没有变化，因此不记
  事件。这与 hook 路径不同——hook 能看见那是两次（子设计 03 的 `DUPLICATE_WINDOW`）。

## 7. 测试策略

`Inferrer` 单测六种情形：

1. 首次收敛只写基线，不产生事件；
2. 收敛版本变化，记一条 `inferred`；
3. 混合版本 / 有机器失联 / 没有任何 running 观测时，不记事件**且不动状态**；
4. 同一版本连续多轮，幂等；
5. **回滚到很久以前的版本仍然记一条**（专门守时间边界，是去重规则最容易写错的地方）；
6. 收敛期内已有同版本 hook 事件时让位不记。

真实 fake host 的链路测试一条：起 V1 容器 → 轮询（建立基线，历史为空）→ 换成 V2 容器
→ 轮询 → 历史出现一条「面板推断」的 V2，且**没有**触发任何告警。

system 测试一条：历史表里两种来源的行各自显示正确的来源文字，推断行的 performer /
command 为 `—`、观测列为「面板观测到」。
